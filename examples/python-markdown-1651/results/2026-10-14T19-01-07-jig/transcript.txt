Fixed. Here's what was happening and what I changed.

**Cause:** In Python 3.13.6, `html.parser.HTMLParser.goahead` changed to match the HTML5 spec. When an end tag like `</dev/null` has no closing `>`, `parse_endtag` returns `-1` and `goahead`, at end of input, discards *all* remaining buffered data instead of emitting it as text (older Pythons fell back to `handle_data`). Markdown's `_HTMLParser` let that `-1` propagate, so everything from `</dev/null` to the end of the document vanished silently.

**Changes**
- `markdown/htmlparser.py`: `_HTMLParser.parse_endtag` now checks the base result; if the end tag can't be parsed (`-1`), it emits the `</` as data and continues. Markdown always feeds a complete block (as the module's entity monkey-patches note), so waiting for more data is unnecessary. This also covers cases where a `>` exists later but can't terminate the tag, e.g. a backtick in `</dev\`>`.
- `tests/test_syntax/blocks/test_html_blocks.py`: added `test_unclosed_endtag_with_name` (the exact reported case) and `test_unclosed_endtag_in_code_span` (`2</dev/null`, `cat </etc/hosts`). These are also picked up by the `md_in_html` test class, which subclasses this one.
- `docs/changelog.md`: Unreleased entry (no issue number, since I don't know it — add one if you have it).
